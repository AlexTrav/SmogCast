# SmogCast – данные

Почасовой ряд концентрации PM2.5 и погоды в Алматы с 01.09.2022 по текущий час –
[series/almaty.csv](series/almaty.csv) (около 36 тыс. часов, 2,7 МБ). Ряд хранится в репозитории
и дописывается скриптом сбора.

## Сбор и проверка

Всё запускается в Docker, локальное окружение Python не нужно:

```bash
make update   # дописать свежие часы (последние 7 дней перезапрашиваются) и проверить ряд
make full     # выгрузить весь ряд заново
make check    # только проверить ряд
make test     # pytest сбора и проверки (без обращения к сети)
```

Повторный запуск в тот же час ничего не меняет: выгрузка воспроизводима.

## Архив прошлых прогнозов погоды

[series/weather_prev.csv](series/weather_prev.csv) – прогнозы ECMWF IFS 0,25° из
[Open-Meteo Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api) с 04.02.2024 (около 24 тыс.
часов, 3,5 МБ): для каждого часа – значение текущего расчёта (`_d0`) и прогнозы, выпущенные за 1–4 суток
до этого часа (`_d1` … `_d4`), для температуры, влажности (с 04.03.2024), ветра, его направления, давления,
осадков и облачности. Нужен, чтобы модели с погодой получали прогноз погоды, известный в момент прогноза,
а не фактическую погоду будущего. Обновление – `make prev` (до вчерашнего дня). В архиве погода другой
сетки (0,25°), чем в ряду (`ecmwf_ifs`, около 9 км): архив `ecmwf_ifs` в Previous Runs есть только
с октября 2025.

## База и ежечасное обновление

Живой ряд хранится в Postgres ([Neon](https://neon.com), бесплатный тариф, Франкфурт, Postgres 18);
CSV в репозитории остаётся замороженным снимком для исследования. Каждый час (в xx:17 UTC) внешний
будильник [cron-job.org](https://cron-job.org) вызывает задачу [GitHub Actions](../.github/workflows/hourly.yml)
через GitHub API, и она запускает `python -m collect hourly`:

1. дописывает в таблицу `series` новые часы (последние 7 дней перезапрашиваются и обновляются);
2. сохраняет снимки прогнозов – `cams_forecasts` (PM2.5 и PM10 от CAMS, около 4 суток вперёд)
   и `weather_forecasts` (8 переменных модели ECMWF IFS на 5 суток): по ним модели получат погоду
   «как она была известна в момент прогноза», а прогноз CAMS станет эталоном для сравнения.
   Снимок пишется, только если прогноз изменился (CAMS пересчитывается 2 раза в сутки, IFS – до 4),
   поэтому `issued_at` – час, когда новый прогноз стал известен, а прогноз, известный в момент t, –
   последний снимок с `issued_at <= t`;
3. если база больше порога `DB_LIMIT_MB` (по умолчанию 100 МБ), удаляет самые старые снимки прогнозов,
   пока размер не опустится до 80 % порога, и сжимает таблицы (`vacuum full`); ряд и журнал не чистятся,
   снимки моложе 14 суток не удаляются никогда;
4. пишет запуск в журнал `runs`: длительность, сколько часов добавлено, сколько строк снимков записано
   и удалено, размер базы, ошибки.

Этапы независимы: если ряд не обновился, снимки прогнозов всё равно сохраняются – задним числом
их не восстановить; снимки CAMS и погоды запрашиваются и пишутся порознь, сбой одного источника не теряет
другой. Повторный запуск в тот же час ничего не дублирует (`insert … on conflict do update`).

Чтобы запись не терялась, запуск идёт в два захода ([live.py](collect/live.py)):

- **сначала сеть, потом база.** Все запросы к Open-Meteo (с повторами они могут идти минутами) выполняются
  при закрытом соединении; запись – по свежему соединению и занимает секунды. Бесплатная Neon засыпает после
  5 минут простоя и рвёт соединение – раньше из-за этого запись падала после долгих повторов;
- **переподключение.** Если соединение всё же оборвалось (`OperationalError`), этап повторяется один раз по
  новому соединению – это безопасно, все этапы записи идемпотентны; так же пишется и строка журнала `runs`;
- **модели считаются и после частичного сбоя сбора** (например, упала только карта): шаг моделей в
  [hourly.yml](../.github/workflows/hourly.yml) выполняется всегда, пересчёт от того же часа перезаписывает прогнозы.

```bash
make seed     # один раз: создать таблицы и загрузить ряд из CSV
make hourly   # ежечасный запуск вручную
make test     # pytest, база – на временном Postgres 18 в docker compose
```

Строка подключения – переменная `DATABASE_URL`: локально в файле `SmogCast/.env` (в git не попадает),
в GitHub Actions – секрет репозитория. Расписание самого GitHub не используется: оно опаздывает
на 5–30 минут, пропускает часы и отключается, если в публичном репозитории 60 дней не было коммитов.
Будильник шлёт `POST /repos/AlexTrav/SmogCast/actions/workflows/hourly.yml/dispatches` с телом
`{"ref":"main"}` и fine-grained токеном только на этот репозиторий (право Actions: read and write);
токен хранится только в cron-job.org и истекает 31.03.2027 – тогда его нужно перевыпустить.

## Источники

| Колонки | Источник | Что это |
|---|---|---|
| `pm2_5`, `pm10`, `no2`, `co`, `so2`, `dust` (мкг/м³) | [Open-Meteo Air Quality API](https://open-meteo.com/en/docs/air-quality-api), домен `cams_global` | расчёт модели CAMS (Copernicus Atmosphere Monitoring Service), сетка 0,4° (около 45 км), узел 43,3° с. ш., 76,9° в. д. |
| `temp`, `dew` (°C), `rh`, `cloud` (%), `wind` (км/ч), `wind_dir` (°), `pressure` (гПа), `precip` (мм) | [Open-Meteo Historical Weather API](https://open-meteo.com/en/docs/historical-weather-api), модель `best_match` | оперативная модель ECMWF IFS: по значениям `best_match` для Алматы совпадает с `ecmwf_ifs` за весь период |

Ключи API не нужны. Данные распространяются по лицензии
[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/): «Air quality data: CAMS / Copernicus,
weather data: ECMWF IFS, via [Open-Meteo.com](https://open-meteo.com/)».

## Как устроен сбор

- Время – в UTC (`2022-09-01T00:00Z`). Местное время Алматы с 01.03.2024 – UTC+5, до этого было UTC+6,
  поэтому в местном времени шкала «прыгает»; переводить в местное время будем только для графиков и признаков.
- Запросы – не больше года за раз; при обрыве соединения, таймауте или ответе 5xx/429 – до 5 попыток с
  паузами 5, 10, 20, 40 с (±20 %, для 429 – по Retry-After), но не дольше 8 минут на все повторы за запуск:
  ежечасная задача укладывается в свои 15 минут и не наползает на следующий час.
- Часы после текущего отбрасываются: API отдаёт их как прогноз, а нужен ряд «по факту».
- Значения последних дней могут уточняться следующими прогонами моделей, поэтому обновление
  перезапрашивает последние 7 дней. Последние часы, где один из источников ещё
  не отдал значение, отбрасываются до следующего обновления.
- Отрицательные концентрации (у пыли в CAMS встречается –1) обрезаются до 0.
- Проверка (`collect/check.py`): ряд начинается 01.09.2022, шкала почасовая без разрывов и повторов,
  нет пропусков, значения в допустимых диапазонах (`RANGES` в `collect/config.py`).

## Ограничения

- **Это не замеры датчиков, а оценка модели CAMS.** Сетка около 45 км усредняет город с горами
  и пригородами, поэтому локальные пики смога в низинах города модель, скорее всего, занижает.
  Прогнозная система учится предсказывать именно эту оценку.
- **Архива прошлых прогнозов CAMS нет**: API принимает переменные `pm2_5_previous_dayN`, но
  возвращает пустые значения. Сравнить свои модели с прогнозом CAMS можно, только если сохранять
  его прогнозы самостоятельно, начиная с текущего момента.
- **Высота пограничного слоя не используется**, хотя важна для инверсий: в архиве ERA5 у Open-Meteo
  она есть только до 31.12.2023, в архиве оперативных прогнозов – с 01.09.2024, между ними дыра в 8 месяцев.
- CAMS global начинается в августе 2022, поэтому в ряду четыре отопительных сезона – мало для
  уверенной оценки годовой сезонности.
- **Ряд неоднороден**: внутри него три обновления модели CAMS (27.06.2023, 12.11.2024, 12.05.2026)
  с заметными сдвигами уровня загрязнителей, а ветер IFS по годам «проседает» относительно реанализа ERA5;
  есть и один сбой CAMS – 60 часов в декабре 2022 без антропогенных выбросов. Ряд здесь хранится
  как есть, разбор и обработка – в [research/](../research/README.md).
